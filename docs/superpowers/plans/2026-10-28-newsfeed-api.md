# NewsFeed API Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A local, fully documented Hono + TypeScript backend for a Facebook-style news feed with bearer auth, presigned media uploads, fan-out-on-write feeds, cursor pagination and offline-sync conflict resolution.

**Architecture:** One Node process (`@hono/node-server`) serving an `OpenAPIHono` app. Postgres (Drizzle) holds all state; MinIO holds media, which clients upload directly with presigned PUT URLs. All like/comment mutations funnel through one function, `applyOperation`, used by both the single endpoints and the batch `/sync` endpoint, so conflict rules live in one place.

**Tech Stack:** Node 24, TypeScript, hono 4.13, @hono/node-server 2.1, @hono/zod-openapi 1.6 (zod 4), @hono/swagger-ui 0.6, better-auth 1.7 (bearer, username, openAPI plugins), drizzle-orm 0.45 + drizzle-kit 0.31 + pg 8, @aws-sdk/client-s3 + s3-request-presigner 3.x, vitest 5, tsx 4, @clack/prompts 1.8, ffmpeg-static (dev only, for generating sample media). Package manager: npm.

**Spec:** `docs/superpowers/specs/2026-10-28-newsfeed-api-design.md` — read it alongside this plan; section numbers below (§) refer to it.

## Global Constraints

- All app routes under `/api/v1`; Better Auth handler at `/api/auth/*`.
- Authenticated routes require `Authorization: Bearer <token>`; missing/invalid → `401 UNAUTHORIZED`.
- Every error body: `{ "error": { "code": string, "message": string, "details"?: unknown } }`.
- Request/response schemas are zod-openapi schemas; the same schema validates and documents (no hand-written duplicate docs for app routes).
- Swagger UI at `/docs`, spec at `/openapi.json`, includes a `bearerAuth` HTTP bearer security scheme and the Better Auth paths.
- Cursor pagination everywhere: default `limit` 20, max 50; response `{ items, nextCursor: string | null }`; cursor is opaque base64url of `(timestamp, id)` keyset.
- Image post: 1–10 images, each ≤ 10 MB (10_485_760 bytes), `image/jpeg|image/png|image/webp|image/heic`.
- Video post: exactly 1 video ≤ 100 MB (104_857_600 bytes), `video/mp4|video/quicktime`, plus optional 1 thumbnail image (image rules).
- Upload session expires 1 hour after creation.
- Follow backfill: latest 50 published posts.
- `/sync` max 100 operations; `/posts/refresh` max 200 posts.
- Future client timestamps more than 60 s ahead of server time are clamped to server time.
- Posts and comments are soft-deleted (`deletedAt`).
- No cloud account or internet needed at runtime; everything via `docker compose`.

## Review Focus

1. **Concurrent replay of the same `clientOpId`** (app fires a retry while the first request is in flight) → exactly one effect, second gets `duplicate`, never a 500. Test in Task 9.
2. **Malformed or tampered cursor** → `400 INVALID_CURSOR`, not a 500 or an empty page. Test in Task 3.
3. **Uploaded file differs from what was declared** (wrong size/type, or a thumbnail declared but never uploaded) → `complete` returns `422 MEDIA_MISMATCH` / `409 UPLOAD_INCOMPLETE` naming the media ids; the post stays unpublished. Test in Task 7.
4. **`complete` called twice, or after expiry** → second call returns the same published post (200); after expiry → `410 UPLOAD_EXPIRED` and the pending post is gone. Test in Task 7.
5. **Like with a far-future clock** (phone clock wrong) must not lock the like state against later corrections → timestamp clamped; a later real-time unlike still applies. Test in Task 9.

### Task 3: Cursor pagination primitives

**Files:**
- Create: `src/lib/cursor.ts`
- Test: `tests/cursor.test.ts`, plus one route-level case added in Task 5

**Interfaces:**
- Produces:
  - `type Cursor = { t: string /* ISO timestamp */; id: string }`
  - `encodeCursor(c: Cursor): string` (base64url of JSON)
  - `decodeCursor(s: string): Cursor` — throws `AppError(400,'INVALID_CURSOR')` on bad base64, bad JSON, missing fields, or unparseable date.
  - `PageQuerySchema` (zod-openapi): `{ cursor?: string; limit: number (coerce, int, 1..50, default 20) }`
  - `pageSchema<T>(item: T)` → zod `{ items: T[]; nextCursor: string | null }`
  - `toPage<R>(rows: R[], limit: number, cursorOf: (r: R) => Cursor): { items: R[]; nextCursor: string | null }` — callers fetch `limit + 1` rows; if more than `limit`, drop the extra and set `nextCursor` from the last kept row.

### Task 9: Interactions — idempotent operations, LWW likes, versioned comments

**Files:**
- Create: `src/modules/interactions/schemas.ts`, `src/modules/interactions/operations.ts`, `src/modules/interactions/likes.ts`, `src/modules/interactions/comments.ts`, `src/modules/interactions/routes.ts`
- Modify: `src/app.ts`
- Test: `tests/interactions.test.ts`

**Interfaces:**
- Consumes: `clampClientTime`, `CommentSchema`, `getUserSummaries`.
- Produces (`schemas.ts`):
  ```ts
  type Operation =
    | { opId: string; type: 'like' | 'unlike'; postId: string; clientTimestamp: string }
    | { opId: string; type: 'comment.create'; postId: string; commentId: string; text: string; clientTimestamp: string }
    | { opId: string; type: 'comment.edit'; commentId: string; text: string; baseVersion: number; clientTimestamp: string }
    | { opId: string; type: 'comment.delete'; commentId: string; clientTimestamp: string };
  type OpStatus = 'applied' | 'duplicate' | 'superseded' | 'conflict' | 'rejected';
  type PostState = { id: string; likeCount: number; commentCount: number; likedByMe: boolean; version: number; deleted: boolean };
  type OpResult = { opId: string; status: OpStatus; error?: { code: ErrorCode; message: string }; canonical: { post?: PostState; comment?: Comment | null } };
  ```
  `OperationSchema` (zod discriminated union on `type`; text 1..2000; ids uuid; `clientTimestamp` ISO datetime), `OpResultSchema`.
- Produces (`operations.ts`):
  - `applyOperation(db: Db, userId: string, op: Operation): Promise<OpResult>` — the single entry point.
  - `getPostState(db, viewerId, postId): Promise<PostState>` (deleted/missing → `deleted: true`, counts 0 when missing).
  - `opResultHttpStatus(r: OpResult): number` — applied/duplicate/superseded → 200 (comment.create applied → 201); conflict → 409; rejected → by code: `POST_DELETED` 410, `POST_NOT_FOUND`/`COMMENT_NOT_FOUND` 404, `COMMENT_DELETED` 410, `FORBIDDEN` 403, `ID_CONFLICT` 409.

`applyOperation` algorithm (one transaction per op):
1. `INSERT INTO client_operation (userId, opId, type, postId, commentId, outcome='pending') ON CONFLICT DO NOTHING RETURNING`. No row → it's a replay: commit nothing else, return `{ status: 'duplicate', canonical: <current state re-read now> }`. (A concurrent identical request blocks on the PK until the first commits, then sees the conflict → duplicate.)
2. Lock the post row `SELECT ... FOR UPDATE` (for comment ops, resolve postId via the comment first). Missing → `rejected POST_NOT_FOUND`; `deletedAt` set or not published → `rejected POST_DELETED`.
3. Dispatch:
   - **like/unlike** (`likes.ts`): `ts = clampClientTime(clientTimestamp)`; load like row. If none or `ts >= row.clientUpdatedAt` → upsert `{ liked, clientUpdatedAt: ts }`; if `liked` actually flipped, adjust `likeCount` ±1 and `version += 1`; status `applied`. Else `superseded`.
   - **comment.create** (`comments.ts`): existing comment with that id → same author & post ⇒ `duplicate`; otherwise `rejected ID_CONFLICT`. Else insert (`clientCreatedAt = clampClientTime`), `commentCount += 1`, `version += 1`, `applied`.
   - **comment.edit**: missing → `rejected COMMENT_NOT_FOUND`; not author → `rejected FORBIDDEN`; deleted → `rejected COMMENT_DELETED`; `baseVersion !== comment.version` → `conflict`; else update text, `comment.version += 1`, `post.version += 1`, `applied`.
   - **comment.delete**: missing → `rejected COMMENT_NOT_FOUND`; not comment author and not post author → `rejected FORBIDDEN`; already deleted → `applied` (no-op); else set `deletedAt`, `commentCount -= 1`, `post.version += 1`, `applied`.
4. Update `client_operation.outcome` to the final status (or error code); commit. Rejections still record the op so a replay is `duplicate` with fresh canonical state.
5. `canonical.post` = `getPostState` after the change; `canonical.comment` = serialized comment for comment ops (`null` if deleted/missing).

- Routes (each takes `opId` as `clientOpId` + `clientTimestamp` in the body and builds the `Operation`; respond with `OpResult` and `opResultHttpStatus`):
  - `PUT /api/v1/posts/:id/like`, `DELETE /api/v1/posts/:id/like` (body `{ clientOpId, clientTimestamp }`)
  - `POST /api/v1/posts/:id/comments` (`{ id, text, clientOpId, clientTimestamp }`)
  - `PATCH /api/v1/comments/:id` (`{ text, baseVersion, clientOpId, clientTimestamp }`)
  - `DELETE /api/v1/comments/:id` (`{ clientOpId, clientTimestamp }`)
